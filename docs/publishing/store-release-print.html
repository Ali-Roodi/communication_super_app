آنچه در build فعلی درست است

بررسی شد و نیازی به تغییر ندارد — چند موردش دقیقاً همان چیزهایی‌اند که معمولاً باعث reject می‌شوند.

  • applicationId = ir.hamrasan.app — پیشوند com.example سیگنال منفی است. namespace که هنوز com.example.… مانده اهمیتی ندارد؛ فروشگاه فقط applicationId را می‌بیند.
  • امضای release — enableV1Signing=false، V2 و V3 روشن. V3 یعنی امکان key rotation در آینده.
  • isMinifyEnabled + isShrinkResources با keep-ruleهای اختصاصی.
  • allowBackup=false + dataExtractionRules — برای اپی که کل mailbox را در SQLite نگه می‌دارد، یک برگ برنده در بخش privacy.
  • Crash reporting پیش‌فرض خاموش؛ بدون DSN چیزی ارسال نمی‌شود و هر رشته‌ی ≥۴ رقم redact می‌شود.
  • keystore داخل repo نیست — key.properties و *.jks هر دو gitignore شده‌اند.

اقدامات

۱. حذف RECORD_AUDIO انجام شد ۱۴۰۵/۰۶/۱۸

اعلام شده بود ولی grep روی lib/ و android/app/src/main هیچ ارجاعی به MediaRecorder / AudioRecord پیدا نکرد، و هیچ‌کدام از پلاگین‌های pubspec هم صوتی نیستند.

خط از manifest حذف شد و جای آن یک کامنت نشست که توضیح می‌دهد چرا عمداً غایب است — تا کسی دوباره برای فیچری که هنوز وجود ندارد اضافه‌اش نکند.

۲. صفحه‌ی privacy policy با URL عمومی انجام شد ۱۴۰۵/۰۶/۲۴

فیلد اجباری فرم انتشار هر دو فروشگاه؛ بدون آن اصلاً نمی‌شود submit کرد.

متن لازم (چهار جمله): داده‌ها فقط روی دستگاه در SQLite ذخیره می‌شوند · هیچ پیام یا مخاطبی به سروری ارسال نمی‌شود · backup سیستمی غیرفعال است · گزارش خطا پیش‌فرض خاموش و بدون محتوای پیام است.

نیمه‌ی اول — انجام شد: متن به‌صورت صفحه‌ی داخل برنامه نوشته شد — PrivacyPolicyPage، از تنظیمات ← «درباره برنامه» ← «حریم خصوصی و دسترسی‌ها». ساختارش از روی manifest است، نه از روی یک متن حقوقی عمومی: یک کارت به‌ازای هر گروه مجوز (مخاطبین، تماس‌ها، پیامک‌ها، اعلان‌ها، موقعیت مکانی، اینترنت) که می‌گوید با آن مجوز چه می‌کند و — مهم‌تر — چه نمی‌کند؛ بعد چهار جمله‌ی بالا زیر «داده‌های شما»؛ بعد فهرست «آنچه هم‌رسان انجام نمی‌دهد». کارت هر مجوز runtime وضعیت فعلی grant را هم نشان می‌دهد (فقط خوانده می‌شود، هرگز درخواست نمی‌شود — قانون PermissionGate). متن مرجع privacy policy همین صفحه است؛ نسخه‌ی وب (docs/privacy/index.html) از روی آن نوشته شده، نه برعکس.

قانون نگهداری: مجوزی که به manifest اضافه می‌شود در همان commit یک کارت این‌جا می‌گیرد. policy ای که یک مجوز اعلام‌شده را جا بیندازد اولین چیزی است که بازبین می‌بیند.

نیمه‌ی دوم — وضعیت URL: https://ali-roodi.github.io/communication_super_app/privacy/ — GitHub Pages از شاخه‌ی main، پوشه‌ی /docs. فایل مرجع: docs/privacy/index.html.

۳. پشتیبان آفلاین از upload-keystore.jks انجام شد ۱۴۰۵/۰۶/۲۴

در بازار و مایکت معادلی برای Play App Signing وجود ندارد. این فایل به‌علاوه‌ی سه رمز داخل key.properties تا همیشه هویت اپ است.

پیامد از دست دادنش: هرگز نمی‌شود برای ir.hamrasan.app بروزرسانی داد؛ تنها راه انتشار مجدد با package name جدید است — یعنی از دست دادن تمام نصب‌ها و دیتای کاربران.

چه شد: scripts/backup_keystore.ps1 و scripts/backup_keystore.sh اضافه شدند. خروجی یک آرشیو hamrasan-keystore-backup-<تاریخ>.tar.enc است (AES-256-CBC، PBKDF2 با ۶۰۰ هزار دور) که .jks، key.properties، نسخه‌ی base64 کلید، یک RESTORE.md با اثر انگشت گواهی و دستور بازیابی، و SHA256SUMS را در خود دارد. هیچ‌چیز بیرون آرشیو به شکل خام نوشته نمی‌شود.

دو چیز این را از «کپی» به «پشتیبان» تبدیل می‌کند: قبل از بسته‌بندی keystore با رمزهای داخل key.properties باز می‌شود (keytool -list) — پشتیبانی که رمزش غلط ثبت شده باشد بی‌ارزش است؛ و بعد از بسته‌بندی آرشیو دوباره باز می‌شود، .jks بایت‌به‌بایت مقایسه می‌شود و keytool روی نسخه‌ی بازیابی‌شده اجرا می‌شود.

اثر انگشت SHA-256 گواهی: 58:BC:0E:5F:2F:C3:B5:BE:6F:5E:5B:AF:F0:C5:B0:2F:E7:BD:9A:8E:CA:D0:6F:86:B4:E0:E1:74:B3:C3:97:0A — همان چیزی که apksigner verify --print-certs روی هر APK فروشگاهی باید نشان بدهد.

رمز آرشیو در repo، آرشیو و گوشی نیست و قابل بازیابی هم نیست؛ در password manager، جدا از آرشیو. تست بازیابی با backup_keystore.sh --restore انجام شد (آرشیوی که PowerShell ساخته بود با bash باز شد، .jks یکسان؛ رمز غلط رد می‌شود).

هنوز باقی است: یک کپی روی USB یا دستگاهی که همیشه کنار لپ‌تاپ نباشد — گوشی تست و لپ‌تاپ معمولاً با هم‌اند. هر وقت USB وصل بود: .\scripts\backup_keystore.ps1 -OutDir E:\.

۴. تصمیم درباره‌ی armeabi-v7a تصمیم محصولی

بلوک packaging { jniLibs { excludes … } } عمداً بقیه‌ی ABIها را حذف می‌کند و دلیلش درست است: دایرکتوری خالی v7a باعث می‌شد دستگاه ۳۲بیتی نصب کند و در اولین اجرا با UnsatisfiedLinkError کرش کند.

نتیجه‌ی فروشگاهی‌اش این است که آن دستگاه‌ها در بازار پیام «ناسازگار» می‌بینند.

دو گزینه: پذیرفتن این محدودیت، یا ساختن یک APK دوم برای armeabi-v7a در همان pipeline (بازار چند APK برای یک نسخه را پشتیبانی می‌کند؛ برای مایکت باید تأیید شود). گزینه‌ی دوم فقط تغییر در pipeline است، نه در کد اپ. تصمیم گرفته‌شده: هنوز نه.

۵. جدا کردن versionCode از pubspec.yaml انجام شد ۱۴۰۵/۰۶/۱۸

scripts/release_build.ps1 و scripts/release_build.sh اضافه شدند. build فروشگاهی از این مسیر ساخته می‌شود:

مقدارمنبع
versionNameتگ روی HEAD (v1.2.3 ← 1.2.3)؛ اگر تگ نبود، از pubspec با اخطار
versionCodegit rev-list --count HEAD

چرا commit count و نه شماره‌ی اجرای CI: همان عدد است چه build روی لپ‌تاپ اجرا شود چه روی runner، هیچ state ای جایی نگه داشته نمی‌شود، و فقط زیاد می‌شود — برخلاف شمارنده‌ی هر workflow که برای یک branch جدید از ۱ شروع می‌کند.

اسکریپت دو گارد دارد: اگر working tree کثیف باشد اخطار می‌دهد، و اگر apksigner verify --print-certs بگوید Android Debug build را رد می‌کند — دقیقاً همان چیزی که fallback به debug key در build.gradle.kts می‌تواند بی‌سروصدا تولید کند.

۶. تصمیم درباره‌ی PROCESS_OUTGOING_CALLS تازه پیدا شد

هنگام حذف RECORD_AUDIO معلوم شد این permission هم هیچ استفاده‌ای ندارد: نه NEW_OUTGOING_CALL receiver ای در manifest هست و نه ارجاعی در Kotlin یا Dart. از Android 10 هم عملاً کنار گذاشته شده (مسیر شماره‌گیر پیش‌فرض CallRedirectionService است).

اقدام پیشنهادی: حذف شود. چون برخلاف RECORD_AUDIO احتمال دارد به مسیر نقش شماره‌گیر گره خورده باشد، اول روی دستگاه واقعی تأیید شود و بعد در همان commit حذف گردد.

طرح CI/CD (نوشته نشده)

Trigger: تگ v*.*.* روی main + workflow_dispatch با ورودی درصد rollout.

  1. Gate — flutter analyze و flutter test؛ رد شد، هیچ آپلودی انجام نمی‌شود.
  2. بازسازی keystore — دیکد KEYSTORE_BASE64 و ساخت android/key.properties در runner.
  3. Build + تأیید امضا — scripts/release_build.sh. همان اسکریپتی است که محلی هم اجرا می‌شود، پس CI و لپ‌تاپ نمی‌توانند از هم فاصله بگیرند.
  4. آپلود بازار — اکشن matinzd/cafebazaar-release با cafebazaar-pishkhaan-api-secret، staged_rollout_percentage، changelog_fa.
  5. آپلود مایکت — اسکریپت اختصاصی (اکشن رسمی وجود ندارد).
  6. Artifact — نگهداری APK و mapping.txt مربوط به R8؛ بدون آن stack traceهای release خوانده نمی‌شوند.
  7. ثبت — نوشتن versionCode منتشرشده در جدول تاریخچه‌ی سند.
