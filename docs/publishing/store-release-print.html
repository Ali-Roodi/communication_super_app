متن لازم (چهار جمله): داده‌ها فقط روی دستگاه در SQLite ذخیره می‌شوند · هیچ پیام یا مخاطبی به سروری ارسال نمی‌شود · backup سیستمی غیرفعال است · گزارش خطا پیش‌فرض خاموش و بدون محتوای پیام است.

نیمه‌ی اول — انجام شد (۱۴۰۵/۰۶/۲۴): متن به‌صورت صفحه‌ی داخل برنامه نوشته شد — PrivacyPolicyPage (lib/features/settings/screens/privacy_policy_page.dart)، از تنظیمات → «درباره برنامه» → «حریم خصوصی و دسترسی‌ها». متن مرجع privacy policy همین صفحه است؛ نسخه‌ی وب باید از روی آن نوشته شود، نه برعکس، تا چیزی که بازبین فروشگاه می‌خواند و چیزی که کاربر می‌خواند یکی باشد.

ساختار صفحه از روی manifest است، نه از روی یک متن حقوقی عمومی: یک کارت به‌ازای هر گروه مجوز (مخاطبین، تماس‌ها، پیامک‌ها، اعلان‌ها، موقعیت مکانی، اینترنت) که می‌گوید با آن مجوز چه می‌کند و — مهم‌تر — چه نمی‌کند (ضبط تماس نه، میکروفون نه، سرور نه)؛ بعد چهار جمله‌ی بالا زیر «داده‌های شما»؛ بعد فهرست «آنچه هم‌رسان انجام نمی‌دهد». کارت هر مجوز runtime وضعیت فعلی grant را هم نشان می‌دهد (فقط خوانده می‌شود، هرگز درخواست نمی‌شود — قانون PermissionGate) و کارتِ ردشده به صفحه‌ی app-info سیستم می‌رود.

قانون نگهداری: مجوزی که به manifest اضافه می‌شود در همان commit یک کارت این‌جا می‌گیرد. policy ای که یک مجوز اعلام‌شده را جا بیندازد اولین چیزی است که بازبین می‌بیند.

نیمه‌ی دوم — انجام شد (۱۴۰۵/۰۶/۲۴): همین متن به‌صورت docs/privacy/index.html (یک فایل HTML استاتیک، فونت از Google Fonts با fallback، لوگو inline) نوشته شد و از GitHub Pages سرو می‌شود — repo عمومی شد، Pages از شاخه‌ی main و پوشه‌ی /docs.

✅ ۳. پشتیبان آفلاین از upload-keystore.jks — انجام شد (۱۴۰۵/۰۶/۲۴)

در بازار و مایکت معادلی برای Play App Signing وجود ندارد. این فایل به‌علاوه‌ی سه رمز داخل key.properties تا همیشه هویت اپ است. از دست رفتنش یعنی هرگز نمی‌شود برای ir.hamrasan.app بروزرسانی داد؛ تنها راه، انتشار مجدد با package name جدید است — یعنی از دست دادن تمام نصب‌ها و دیتای کاربران.

چه شد: scripts/backup_keystore.ps1 و scripts/backup_keystore.sh اضافه شدند. خروجی یک آرشیو hamrasan-keystore-backup-<تاریخ>.tar.enc است (AES-256-CBC، PBKDF2 با ۶۰۰ هزار دور) که .jks، key.properties، نسخه‌ی base64 کلید (همان چیزی که secret CI می‌خواهد)، یک RESTORE.md با اثر انگشت گواهی و دستور بازیابی، و SHA256SUMS را در خود دارد. هیچ‌چیز بیرون آرشیو به شکل خام نوشته نمی‌شود؛ خود پوشه‌ی keystore-backup/ هم gitignore است.

دو چیز این را از یک «کپی» به «پشتیبان» تبدیل می‌کند و هر دو در همان اجرا انجام شد:

  • قبل از بسته‌بندی، keystore با رمزهای داخل key.properties باز می‌شود (keytool -list). پشتیبانی که رمز ثبت‌شده‌اش غلط باشد هیچ ارزشی ندارد و این تنها لحظه‌ای است که فهمیدنش ارزان است.
  • بعد از بسته‌بندی، آرشیو دوباره باز می‌شود، .jks بایت‌به‌بایت با اصل مقایسه می‌شود و keytool روی *همان نسخه‌ی بازیابی‌شده* اجرا می‌شود. اثر انگشتی که گزارش می‌شود از نسخه‌ی بازیابی‌شده است، نه اصل.

اثر انگشت SHA-256 گواهی: 58:BC:0E:5F:2F:C3:B5:BE:6F:5E:5B:AF:F0:C5:B0:2F:E7:BD:9A:8E:CA:D0:6F:86:B4:E0:E1:74:B3:C3:97:0A — همین چیزی است که apksigner verify --print-certs روی هر APK فروشگاهی باید نشان بدهد.

⬜ ۴. تصمیم درباره‌ی armeabi-v7a — تصمیم محصولی، نه باگ

بلوک packaging { jniLibs { excludes … } } عمداً بقیه‌ی ABIها را حذف می‌کند و دلیلش درست است (دایرکتوری خالی v7a باعث نصب موفق روی دستگاه ۳۲بیتی و UnsatisfiedLinkError در اولین اجرا می‌شد). نتیجه‌ی فروشگاهی‌اش: آن دستگاه‌ها در بازار پیام «ناسازگار» می‌بینند.

دو گزینه: پذیرفتن این محدودیت، یا ساختن یک APK دوم برای armeabi-v7a در همان pipeline (بازار چند APK برای یک نسخه را پشتیبانی می‌کند؛ برای مایکت باید تأیید شود). گزینه‌ی دوم فقط تغییر در pipeline است، نه در کد اپ.

اسکریپت دو گارد هم دارد: اگر working tree کثیف باشد اخطار می‌دهد (APK با هیچ commit ای مطابقت ندارد)، و اگر apksigner verify --print-certs بگوید Android Debug build را رد می‌کند — دقیقاً همان چیزی که fallback به debug key در build.gradle.kts می‌تواند بی‌سروصدا تولید کند.

version: 1.0.0+1 در pubspec دست‌نخورده ماند و حالا کامنت بالایش می‌گوید که آن +1 فقط برای development محلی است. versionCode/versionName در build.gradle.kts هم کامنت گرفتند.

تأیید عملی (۱۴۰۵/۰۶/۱۸): اسکریپت تا انتها اجرا شد. aapt2 dump badging روی APK ساخته‌شده: versionCode='122' versionName='1.0.0'، و گارد امضا گواهی CN=Hamrasan, OU=Hamrasan App, O=Hamrasan, L=Tehran, ST=Tehran, C=IR را خواند و تأیید کرد.

دو ایراد که همان اجرا نشان داد و اصلاح شدند — هر دو از جنس «بی‌صدا رد شدن»:

  • apksigner یک ابزار JVM است و روی ماشینی بدون java در PATH فقط JAVA_HOME is not set چاپ می‌کرد. اسکریپت در آن متن دنبال Android Debug می‌گشت، پیدا نمی‌کرد، و امضا را تأیید می‌کرد — یعنی دقیقاً برعکس کاری که این گارد برایش هست. حالا JBR همراه Android Studio به‌عنوان fallback ست می‌شود و نبودِ certificate DN: در خروجی یک خطا است، نه یک تأیید.
  • android/local.properties در gitignore است، پس روی runner وجود ندارد و خواندنش زیر set -e اسکریپت را بعد از یک build موفق می‌کشت. حالا اول ANDROID_HOME / ANDROID_SDK_ROOT خوانده می‌شود. ضمناً ویندوز فقط apksigner.bat دارد و لینوکس فقط نسخه‌ی بدون پسوند؛ هر دو glob می‌شوند.

⬜ ۶. تصمیم درباره‌ی PROCESS_OUTGOING_CALLS — تازه پیدا شد

هنگام حذف RECORD_AUDIO معلوم شد این permission هم هیچ استفاده‌ای ندارد: نه NEW_OUTGOING_CALL receiver ای در manifest هست و نه ارجاعی در Kotlin یا Dart. از Android 10 هم عملاً کنار گذاشته شده (مسیر شماره‌گیر پیش‌فرض CallRedirectionService است، نه این).

دقیقاً از همان جنس ریسکی است که RECORD_AUDIO بود: یک dangerous permission که reviewer دلیلی برایش پیدا نمی‌کند.

اقدام پیشنهادی: حذف شود. چون برخلاف RECORD_AUDIO احتمال دارد به مسیر نقش شماره‌گیر گره خورده باشد، اول روی دستگاه واقعی تأیید شود و بعد در همان commit حذف گردد.

  6. Artifact — نگهداری APK و mapping.txt مربوط به R8؛ بدون آن stack traceهای release خوانده نمی‌شوند.
  7. ثبت — نوشتن versionCode منتشرشده در جدول تاریخچه‌ی همین فایل.
