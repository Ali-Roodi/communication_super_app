# Dual SIM

Part of the architecture notes for this repo. Index and the rules that apply everywhere: [`DEVELOPER_GUIDE.md`](../DEVELOPER_GUIDE.md).

### Dual SIM

`lib/core/sim/` (model · service · bloc · widgets) over `android/.../sim/SimRegistry.kt` + `SimHandler.kt`. Google Messages' and Google Phone's behaviour, followed exactly:

- **One SIM ⇒ nothing changes.** Every affordance — the composer chip, the pickers, the bubble/call-log badges, the notification subtext, the «ذخیره در» row — hangs off `SimService.isMultiSim`. A single-SIM phone must look byte-identical to the app before this existed.
- **The identity that travels is the `subscriptionId`; the *slot* is only ever displayed.** A subscription id is an opaque per-device counter that changes when a card is re-inserted, so a stored preference names the subscription while «سیم ۱» names the tray.
- **NULL means unknown, never SIM 1.** `messages.subscription_id`, `call_logs.subscription_id` and `CallInfo.subscriptionId` are null for provider rows the OEM never stamped and for VoIP calls. A wrong SIM badge is worse than none, so the UI omits it.
- **`SimRegistry` is an `object`, not a handler**, because `SmsNotifier`, `IncomingSmsReceiver` and `ScheduledSmsWorker` need SIM answers *while the Flutter engine is dead*. Every read is wrapped: `SubscriptionManager` throws until READ_PHONE_STATE is granted and the app must degrade to "single, unknown SIM" rather than drop an SMS.
- **Telecom names a `PhoneAccountHandle`, not a subscription — ask telephony which is which.** `SimRegistry.subscriptionOfHandle` is `TelephonyManager.getSubscriptionId(handle)` (API 30+; on 26–29 `createForPhoneAccountHandle` + the then-hidden `getSubscriptionId()`, reflectively), and `phoneAccountFor` / `subscriptionIdForAccountId` start from it. Only when it cannot answer do they guess: `handle.id == subId` (modern AOSP — the SM A336E: id `"10"`), the ICC ID (unreadable for an app since Android 10, so useless exactly on the older builds whose handle id *is* the ICC ID), a label **only when one account carries it**, slot order only with one account per card. The label guess used to take the first match — and two cards of one carrier (two Irancell or two MCI lines, the common case) share a label, so SIM 1's calls could leave on SIM 2. When telephony named a card for every account and none is the requested one, the answer is null, never a guess. The same mapping serves outgoing calls (`EXTRA_PHONE_ACCOUNT_HANDLE`) and the call log's `PHONE_ACCOUNT_ID`; Dart caches it in `SimService.subscriptionForAccountId`.
- **A call's SIM is asked of telephony with the whole account**, not its id string (`SimRegistry.subscriptionOfAccount`): the call screen and the missed-call card pass the live `PhoneAccountHandle`, and the call log rebuilds one per row from `PHONE_ACCOUNT_COMPONENT_NAME` + `PHONE_ACCOUNT_ID` and resolves it natively (cached per account; the row's `subscriptionId`). Looking the account up by its id alone is why calls on SIM 2 carried no SIM at all on a dual-SIM phone whose ids are not subscription ids: the id is the subscription id on the SM A336E (`10`, `13`) but the ICC ID or something else elsewhere. ICC IDs are compared tolerantly (`iccMatches`: `F` padding, case, a trailing check digit — `IccMatchTest`).
- **Which card an ordinary call or SMS uses — the product rule (1405/07/27): "from the phone's default at first, then a personal choice for each".** In order:
  0. **for a call while another is up** («افزودن تماس», a call-back from a notification mid-call): the card of that call (`CallRoute.LIVE_CALL`). A dual-SIM phone holds one card in a call at a time; the SM A336E cancelled a second leg dialled on the other card before it left the phone (`OUTGOING_CANCELED`) and the user saw nothing — found 1405/07/29 when a contact pinned to SIM 1 was added to a call on SIM 2. This is about which card *can* carry the call, so it outranks every preference below;
  1. a card picked for this one call (long-press, «تماس با سیم …»);
  2. the **contact's** own card («سیم‌کارت تماس», `Phone.PREFERRED_PHONE_ACCOUNT_*`) — for calls; the **conversation's** («ارسال با») — for SMS;
  3. the **app's** default, Settings → «سیم‌کارت‌ها» (`SimSettingsPage`, `SimService.setAppDefault`): «پیش‌فرض گوشی» until changed, a card, or (calls) «هر بار بپرس»;
  4. the **phone's** default;
  5. otherwise ask.
  **The rule lives natively** (`SimRegistry.routeFor` for calls, `defaultSmsFor` + `thread_sim` for SMS), because the missed-call «تماس», the notification quick reply and a call another app starts are placed with no Flutter engine. The app's default is mirrored there (`setAppDefaults` → SharedPreferences `sim_prefs`). Dart asks `callRoute` only to decide whether to show the picker; every routed dial goes out with **no** card named and native applies the same rule.
- **The phone's default for calls is telecom's own** (`TelecomManager.getUserSelectedOutgoingPhoneAccount`, `SimRegistry.defaultVoiceAccount`), and it is dialled by **not naming a card at all** — telecom then uses exactly what Android's settings show. Reported from the field: a phone pinned to SIM 2 dialled on SIM 1 because the app read `SubscriptionManager`'s default voice subscription and passed it back as an explicit account; on some builds the two disagree, or the subscription→account mapping is wrong. SMS still names its card (`SmsManager` for a subscription); that default is `SmsManager.getDefaultSmsSubscriptionId`.
- **A call telecom cannot place without a card** (`STATE_SELECT_PHONE_ACCOUNT`: phone on «ask every time», dial from outside the app) is answered by `CallInCallService.selectAccountFor` — the contact's card, else the subscription default, else the first — because the in-call screen has no account picker and the call would otherwise sit there. The app's own dials never get there: they ask first.
- **The pinned defaults are re-read, not remembered.** `SimService.refreshDefaults` runs before every dial (`callRoute`) and on every return to the foreground (`AppLifecycleListener`).
- **`CallLogService` must `await SimService.instance.ensureLoaded()` before mapping rows.** The mapping's result is *persisted*, so running before the roster exists stamps "no SIM" on every call permanently. `SimBloc` loads at startup but the call-log sync wins that race on a cold start.
- `call_logs` stores the **subscription id** (`subscription_id`), never a slot: a stored slot was once faked (`simDisplayName != null ? 1 : null`, every call on either card claimed «سیم ۱»), and a slot is derived from the subscription when shown.
- **SMS keeps a card per conversation only when the user chose one** (`thread_sim`, `ThreadSimRepository.choose`, from «ارسال با» → «تعویض», which also offers «پیش‌فرض»). A conversation without one sends on the default and follows it when it changes. It used to remember the card of every send and fall back to the card the last message *arrived* on; both made a conversation stick to a card the user never chose, against the product rule. The quick reply reads the same table natively (`SmsNotificationActionReceiver.chosenThreadSim`) — **`thread_sim` is a Kotlin/Dart mirror**.
- **The picker only appears when there is a real choice** (`callRoute` answers `ask`). `placeCall` / `chooseVoiceSim` (`core/sim/sim_call.dart`) are the ONE dial path in the app for exactly this reason — do not call `NativeCallService.makeCall` directly. A dismissed picker is a cancelled call.
- **…but there is ALWAYS an explicit override**, or a pinned default makes the other card unreachable from the app — which is exactly what the first pass got wrong. Two affordances, both through `placeCallPickingSim`: a **long-press on every call button** in the app, and the explicit «تماس با سیم …» rows `simCallRows` adds to the call-log / favourites / number sheets.
- **A call icon with a long-press is `CallIconButton`** (`core/sim/widgets/call_icon_button.dart`) — never an `IconButton` with a `tooltip` inside a `GestureDetector`. That was «اخیر», the search results, the keypad's suggestion and the conversation header, and on a phone the long-press did nothing but show the tooltip «تماس · نگه‌داشتن برای انتخاب سیم‌کارت»: a tooltip opens on long-press through its own recogniser, deeper in the tree, and wins the arena. The words travel as the semantics label instead. Found on the SM A336E.
- **«اخیر» dials by the ordinary rules; the row's card is only a hint.** `CallLogTile`'s call button and the call-detail sheet's «تماس» chip pass `log.sim` as `placeCall(suggested:)` — the card the picker opens on when it has to ask — never as `sim:`. Calling back on the line a call came in on put most calls of a phone pinned to SIM 1 on SIM 2 (reproduced on the SM A336E). The missed-call notification's «تماس» follows the same rule natively and uses the arrival card only on «ask every time», where a notification action has no picker to show.

**The card in use is in sight while a message is written and a number dialled** (`SimChip`, dual-SIM only). They were removed once, after Google Messages and Google Phone, and put back on the mentor's report (1405/08/05): a dual-SIM user who cannot see the card is the one who sends or calls from the wrong one. Each chip names exactly the card the action will use and is resolved by the same rule the action follows — never a second rule of its own.

- The **composer** chip sits inside the pill next to «+». It shows `_sim` — the conversation's own card, else the default — which is the very value the send passes. Tapping it is **the same choice as «ارسال با» on the details page** (`chooseThreadSim`, `messages/screens/widgets/thread_sim_choice.dart`): stored for the conversation at once, «پیش‌فرض» hands it back to the default and the open conversation follows the default again.
- The **keypad** chip sits beside the call pill, balanced by an empty box of the same width so the pill does not move. `DialerCallPill` (stateful) resolves it with `SimService.callRoute` for the typed number (debounced 250 ms; an empty field shows `defaultFor(voice)`), so a contact with a card of their own changes it as the number is typed; «سیم‌کارت» on it means the dial will ask. Tapping it picks a card **for this call**, kept until the field is emptied — the chip is a choice, the pill is the action. While a call is up the second leg can only use that call's card (`CallRoute.liveCall`), so the chip names it and is not tappable, and the pill's long-press is off.
- **`ConversationDetailsScreen`** (`messages/screens/conversation_details_screen.dart`) is Google Messages' details page and is what tapping the conversation header now opens — avatar, name, number, تماس / اطلاعات مخاطب, the **«ارسال با» card with «تعویض»**, then اندازه متن · بایگانی · مسدود · حذف. The header used to go straight to the contact page, which an unsaved number does not have and which is the wrong home for a per-conversation setting. Everything that ends the conversation comes back as a `ConversationDetailsOutcome` rather than being done there — the delete has to take the provider rows with it and the conversation is the screen holding the thread, the same split `GroupDetailsScreen` uses.
- **The card always names a concrete SIM**: the conversation's chosen one, else the default (`ThreadSimRepository.defaultSim`: the app's, else the phone's, else slot 1), shown with «(پیش‌فرض)» when it is not the conversation's own. A page whose job is to print «which card does this go out on» cannot print «none», so the fallback exists and the *send* uses exactly the card that was shown.
- **The send pre-flight is per-SIM.** `SmsHandler.isInService(subscriptionId)` builds a `TelephonyManager.createForSubscriptionId`; reading the *default* subscription's `ServiceState` made the two cards lie about each other — a send on SIM 2 refused with NO_SERVICE because SIM 1 had no signal, and a send on a card that genuinely had none sailing past the check into the radio queue (which reads to the user as "it sent, very late").
- **`SimRegistry.subscriptions` is cached** (30 s TTL, dropped by `OnSubscriptionsChangedListener`). It is several binder round-trips — plus one per SIM for the card's own number on API 33+ — and it sits on the incoming-SMS notification path (twice) and on every telecom call-state change. `withNumbers` is opt-in and uncached: only the Dart picker displays numbers.
- **Never rebuild a `MessageModel` field by field — use `copyWith`.** `MessageBloc._onMessageStatusChanged` and `_mergePersistedMessage` did, and each silently dropped whatever field was added last: a bubble lost its SIM badge the instant its ✓✓ landed and only got it back on the next read from the DB.
- **Scheduled messages carry `subscription_id`** and `ScheduledSmsWorker` (Kotlin) resolves null to the system default before sending, so the send, the provider row and the chat row all name the same card. Change it with `scheduled_message_model.dart`, as ever.
- **A card going into the phone is not something the element tree can notice.** Every affordance reads the *static* roster synchronously inside `build` (a bubble's badge cannot await a channel), which is correct and is also why the app stayed single-SIM-shaped until it was killed and reopened. `SimService.revision` is bumped whenever the roster or the pinned defaults change, and `SimAware` (`core/sim/widgets/sim_picker.dart`) is the one-line wrapper that turns it into a rebuild — used by the conversation, «اخیر» and the details card. Screens that only read the roster at *gesture* time (a long-press picker, an action sheet) need nothing; the static cache is already current by then.
- **The call screens read the roster through `SimAware`, not once in `build`.** A ringing call is the single most likely thing to wake a dead process, so `IncomingCallScreen` / `InCallScreen` regularly paint before `SimService` has answered — and a one-shot read then decides the phone is single-SIM and prints «تماس ورودی» with no card on it, for the whole call. Both call `ensureLoaded()` from `initState` and wrap the carrier line in `SimAware`. The incoming-call **notification** names the card too (`CallInCallService.subscriptionOf` → `SimRegistry.labelOf`, multi-SIM only): on a locked phone that card is often the only thing the user sees of the call.
- **The roster event does not carry the derived state.** On a change, `SimService._refreshDerived` re-reads `getDefaults` and `getPhoneAccounts`. Without it the roster updated live while `defaults` still said «single SIM, nothing pinned» and the account map still had one entry — so the picker had nothing to pick and every new call was logged with no SIM.

**SIM contacts are NOT in `ContactsContract`.** The provider only carries them once the device's *default* contacts app has registered a SIM account and imported the card — which does not happen on a phone where this app is the contacts surface, so `flutter_contacts` returns the same list with a second SIM inserted as without one. `SimContactsHandler.kt` reads `content://icc/adn/subId/<subId>` per active subscription — **on its own thread, never the main one**: the phone process answers it by reading the card, the first read before anything warmed that cache takes seconds per card on some phones, and on the main thread that froze the whole app the first time the address book was read after install (the mentor's dual-SIM phone; gone on the second launch, when the cache was warm). Each read logs its duration (`read N card(s) in X ms`) — (the bare `content://icc/adn` always resolves to the *default* subscription, so a naive version shows SIM 1's contacts twice), and `ContactRepository._mergeSimContacts` appends them, dropping any whose number the phone book already has. They are `ContactSource.sim`: no photo, no editing in place (an ADN record is one name, one number, a card-set length limit and no durable id), so «ویرایش» becomes «کپی در تلفن» and deletes go through the ICC provider by content match. `ContactBloc` re-reads on every roster change — that is the other half of "the new SIM's contacts never appeared".
